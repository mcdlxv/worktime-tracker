# Журнал работы с ИИ

Журнал ведётся по ходу работы. В нём записано, какой инструмент и какая модель использовались, что у них спросили, что получили, что пошло не так и как это нашли. Выжимка из журнала попадёт в README.

| Инструмент                       | Модель          | Для чего                                          |
| -------------------------------- | --------------- | ------------------------------------------------- |
| Claude Code (десктоп-приложение) | Claude Opus 5.5 | разбор ТЗ, план, архитектура, код по TDD, отладка |

## Как проверяется код, написанный ИИ

- **TDD.** Тест пишется до реализации и сначала должен упасть.
- **Автоматические проверки.** `npm run check` (ESLint, типы, тесты) и `prettier --check` запускаются и локально, и в CI.
- **API по установленным версиям.** API библиотек сверяется с документацией и типами установленных версий (`node_modules/next/dist/docs`, `.d.ts`), а не с памятью модели: у Next 16, Vitest 5 и zod 4 есть несовместимые изменения.
- **Эксперимент перед кодом.** Допущения проверяются экспериментом, прежде чем попасть в код (см. ошибки № 1 и 2).
- **Ревью человеком.** Человек читает дифф каждого этапа.

### 27.10.2026 — этап 1: схема БД и таймер

> Запрос (ответ на варианты, которые предложил ИИ): «Этап 0 посмотрел, всё ок. Начинай этап 1: схема БД и таймер по TDD.»

- Правило «не больше одного идущего таймера на сотрудника» обеспечивает частичный уникальный индекс `WHERE ended_at IS NULL`. Сгенерированный SQL ИИ прочитал сам и дополнительно проверил тестом схемы.
- Каждая задача шла по TDD:
  - сначала тест;
  - запуск и проверка, что тест падает по правильной причине;
  - затем минимальный код.

  Типы и классы ошибок добавлялись только тогда, когда их требовал очередной красный тест.

- Повторный старт. Красный тест показал реальную цепочку ошибки: `DrizzleQueryError` → `LibsqlError` → `SqliteError`. В сообщении SQLite называет колонку, а не индекс, поэтому сервис распознаёт конфликт по тексту сообщения, проходя по цепочке `cause`.
- Попутно выяснилось, что в сообщении `DrizzleQueryError` есть параметры запроса, то есть описание задачи. Значит, HTTP-слой не должен отдавать такие ошибки наружу (учтено в плане, задача 3.1).
- Три теста прошли сразу, и так и должно быть: они сторожат свойства схемы, а не новый код.
  - Старт после стопа: защищает от превращения частичного индекса в обычный уникальный.
  - Вставка в обход сервиса: проверяет сам индекс.
  - Перезапуск: защищает от хранения таймеров в памяти процесса.
- В тест сортировки специально добавлено имя на «Ё». При сортировке по кодам символов «Ё» встаёт раньше «А»; отдельной проверкой подтверждено, что обычный `sort()` ставит «Ёлкину» первой.
- Промах в процессе работы. Проверка Prettier в одной из команд шла через `| tail -1`, поэтому её код возврата терялся, и коммит прошёл с неотформатированным файлом. Это заметили на следующей проверке. Локальный коммит исправлен, а команды переписаны так, чтобы сбой останавливал цепочку.

### 27.10.2026 — этап 2: отчёт за период

> Запрос (ответ на варианты, которые предложил ИИ): «Этап 1 посмотрел, всё ок. Начинай этап 2: отчёт за период по TDD.»

- Вся логика отчёта собрана в трёх чистых функциях (`report.ts`): попадание записи в период, обрезка по границам и сборка отчёта. Они тестируются без базы.
- Суммы считаются в коде. SQL-`SUM()` не подходит: нужна обрезка по границам периода, а на пустом наборе он вернул бы `NULL`.
- Упрощение. В первой версии правила попадания в период была ветка для записи нулевой длины ровно на границе `from`. Ни один тест её не требовал, а в интерфейсе такой случай практически невозможен, поэтому ИИ убрал ветку и оставил стандартное пересечение интервалов. Граничные тесты по-прежнему проверяют знаки `>` и `<`.
- Работа с датами из формы. Тесты явно задают часовой пояс (`TZ`), потому что в CI стоит UTC и там две классические ошибки не видны:
  - `new Date("2026-10-01")` разбирается как полночь UTC, а не местная;
  - конец дня через «+24 ч» теряет час в день перевода часов: 25 октября 2026 года в Берлине длится 25 часов.
- Живой счётчик не уходит в минус, если часы браузера отстают от серверных.
- **Ошибок в коде на этом этапе тесты не поймали.** Красными тесты были только из-за отсутствующих модулей. Чтобы убедиться, что тесты вообще способны ловить ошибки, ИИ провёл мутационные проверки:
  - наивные варианты работы с датами дают другие значения;
  - если сузить SQL-фильтр отчёта до «запись началась внутри периода», падает ровно тест про записи, начатые до периода.

  Такая же проверка сортировки «Ё» была на этапе 1.

### 27.10.2026 — этап 3: HTTP API

> Запрос (ответ на варианты, которые предложил ИИ): «Этап 2 посмотрел, всё ок. Начинай этап 3: HTTP API по TDD.»

- HTTP-логика вынесена в `createApiHandlers`, отдельно от маршрутизации Next.js. Её тестируют обычными объектами `Request` на настоящем сервисе. Файлы маршрутов занимают 3–5 строк.
- Каждую ошибку API возвращает в виде `{ error: { code, message } }`. Статусы задаёт `Record<ErrorCode, number>`. Когда добавили код `INVALID_JSON`, проверка типов упала, пока ему не назначили статус. Значит, проверка полноты работает.
- Неожиданная ошибка превращается в общий ответ 500 и пишется только в серверный лог. Это напрямую следует из находки этапа 1: в сообщении `DrizzleQueryError` есть параметры запроса, а в них данные пользователя.
- Прежде чем писать разбор параметров отчёта, ИИ проверил API zod 4 на живых значениях: `z.iso.datetime` и параметр `error`. Время без часового смещения отклоняется, потому что оно неоднозначно.
- `next build` пометил все API-маршруты как динамические (`ƒ`). Значит, в продакшене нет риска получить пререндеренный ответ с устаревшими данными.
- Живая проверка на dev-сервере: каждый эндпоинт вернул ожидаемый статус, а итог отчёта совпал с разницей между временем стопа и старта. Плагин контекста запретил `curl`, поэтому запросы отправлялись через `fetch`. URL собирался через `URLSearchParams`, то есть кодировался так же, как у `curl --data-urlencode`.
- **Найдено вживую:** незакодированный `+` в смещении (`…+05:00`) сервер читает как пробел и отвечает 400. Клиент приложения шлёт время с `Z`, так что его это не касается. В README примеры `curl` будут с `--data-urlencode`.
- Утверждение о том, какие `.env`-файлы читают скрипты и `next dev`, ИИ проверил по исходнику `@next/env`, прежде чем записать его в план. Общий файл для обоих режимов — `.env.local`.
- Ошибок в коде тесты на этом этапе не поймали.

### 27.10.2026 — автоматическое ревью безопасности

> Источник: автоматическое ревью безопасности (плагин security-guidance) по коммитам этапа 3. Это не запрос человека.
>
> Решение человека: «Добавь защиту от межсайтовых запросов по TDD (Sec-Fetch-Site и Content-Type), запиши в журнал, потом начинай этап 4.»

- Ревью отметило три проблемы:
  1. старт и стоп таймера любого сотрудника без проверки прав (IDOR);
  2. отчёт по всем сотрудникам доступен без входа;
  3. изменяющие POST-запросы не защищены от CSRF.
- Оценка ИИ:
  - Замечания 1 и 2 вытекают из самого ТЗ («Авторизация и сложные роли не нужны»). Они приняты как ограничение и пойдут в README вместе с тем, что нужно для продакшена: вход, роли, проверка прав на уровне сотрудника.
  - Замечание 3 применимо частично. Без входа классического CSRF нет. Но страница чужого сайта может заставить браузер посетителя записать данные в приложение, запущенное на `localhost` или во внутренней сети.
- Красные тесты подтвердили риск: межсайтовый запрос и «простой» POST с `text/plain` создавали сотрудника.
- После исправления тесты зелёные. Подробности — в ошибке № 5 ниже.
- **Не проверено:** настоящую атаку из браузера на `localhost` ИИ не воспроизводил. Вывод сделан по правилам CORS; в свежих версиях Chrome запросы с публичных сайтов на `localhost` ограничены дополнительно.
- **Второе автоматическое ревью** — уже по коммиту с защитой — указало, что она не закрывает DNS rebinding.
  - Суть атаки: домен злоумышленника после загрузки страницы начинает указывать на наш сервер. Для браузера запросы этой страницы становятся запросами к тому же сайту: `Sec-Fetch-Site: same-origin`, и `Content-Type: application/json` можно ставить свободно.
  - ИИ согласился с замечанием. Первоначальный комментарий в коде и эта запись в журнале обещали больше, чем проверка делает: комментарий исправлен, ограничение записано.
  - Закрыть DNS rebinding может только сверка заголовка `Host` с белым списком. Это требует настройки при развёртывании, поэтому решение оставлено человеку.

### 27.10.2026 — этап 4: интерфейс

> Запрос (ответ на варианты, которые предложил ИИ): «Добавь защиту от межсайтовых запросов по TDD (Sec-Fetch-Site и Content-Type), запиши в журнал, потом начинай этап 4.»

- **Дизайн.** Сначала ИИ составил дизайн-план и сверил его со списком типичных «ИИ-шаблонов» (кремовый фон с терракотой, одинаковые карточки, подписи капслоком), а потом уже писал код. Что получилось:
  - метафора учётной книги;
  - один акцент для идущего таймера;
  - шрифт IBM Plex из npm.
- **Отступление от плана.** Вместо shadcn/ui ИИ сделал два своих примитива и взял нативные элементы форм: так в репозитории нет сгенерированного кода.
- **TDD для логики интерфейса:**
  - клиент API: каждый изменяющий запрос, включая стоп, уходит как JSON;
  - пресеты периода;
  - даты в поясе браузера;
  - сид.
- **Что предусмотрено при проектировании, а не найдено потом:**
  - рассинхрон гидратации на странице отчёта: дата по умолчанию известна только браузеру;
  - гонка ответов при быстром переключении периода;
  - дрейф живых часов.
- **ESLint с правилом React Compiler** не пропустил `setState` синхронно внутри эффекта. Загрузку переписали на колбэки промиса.
- **Проверка в браузере нашла пять проблем**, все исправлены:
  - на телефоне строка с идущим таймером выходила за экран — ошибка № 6;
  - строка записи в отчёте выходила за край на 4 px;
  - скринридер читал имя и цифры слитно;
  - сообщение об ошибке не исчезало после правки поля;
  - после потери связи не было кнопки «Повторить».
- **Ошибки ИИ, пойманные замером:**
  - Скриншоты встроенного браузера дважды показали обрезанную страницу. ИИ ничего не стал «чинить», а сначала измерил геометрию DOM: переполнения не было, и это оказался артефакт масштаба при съёмке. Только третье подозрение, на телефонной ширине, подтвердилось замером (`scrollWidth` 482 при окне 375 px).
  - Стрелка раскрытия в отчёте якобы не поворачивалась, и ИИ добавил `inline-block` с комментарием. Замер свойства `rotate` показал, что поворот работал и раньше: элемент внутри flex-контейнера и так блочный. Правку и неверный комментарий ИИ удалил.
- **Перезапуск проверен по-настоящему.** Процесс сервера остановлен: порт свободен, запросы падают. После нового запуска идущий таймер продолжил отсчёт с тем же `startedAt`.
- **Найдено попутно — решает человек.** Стоп, нажатый, пока сервер лежал, сработал примерно через 40 секунд, уже после запуска: запрос доставили повторно (прокси панели или браузер). Это показало, что `POST /timer/stop` не привязан к конкретной записи. Опоздавший или повторный запрос остановил бы новый таймер, запущенный за это время. ИИ предложил останавливать по `entryId`.

### 27.10.2026 — стоп по идентификатору записи

> Запрос (ответ на варианты, которые предложил ИИ): «Сделай стоп по entryId по TDD, защиту от DNS rebinding (белый список Host) опиши в README как ограничение, потом переходи к этапу 5.»

- **Регрессионный тест.** Сначала написан тест на найденный случай: старт A → стоп A → старт B → опоздавший «стоп A». Ждём 409, а B продолжает идти. Затем `POST /api/time-entries/:id/stop` заменил стоп по сотруднику. Остался один способ остановить таймер, на него перешли клиент, интерфейс, сид и тесты.
- **Проверка типов поймала ошибку ИИ, которую пропустил Vitest.** `super(...NOT_FOUND[what])` разворачивал объединение кортежей, а TypeScript так не умеет. Таблицу переделали на объекты.
- **Проверка в браузере дала 500** — это ошибка № 8 ниже. Тесты её не видели. Исправлено и перепроверено на том же сервере: тот же стоп вернул 200.
- **Сетевой журнал браузера объяснил опоздавший стоп из этапа 4.** Запрос упал с `ERR_CONNECTION_REFUSED`, и браузер отправил его заново. Повторную отправку делает окружение, а не код приложения.
- **DNS rebinding описан в README как ограничение:** как работает атака, как её закрыть белым списком `Host` и почему это не сделано.

### 27.10.2026 — этап 5: e2e, чистый клон, независимое ревью

> Запрос: тот же, что в предыдущем разделе («…потом переходи к этапу 5»).

- **E2E на Playwright.** Тесты идут на production-сборке со своим портом и своей БД, в двух проектах: desktop и телефон (Pixel 7); в CI это отдельный шаг. Два отступления от плана описаны в [plan.md](plan.md), задача 5.1:

  - БД между прогонами не удаляется, данные разных прогонов различаются уникальными именами.

  Первый прогон поймал ошибку в самом тесте: проверка отчёта нашла запись, оставленную другим прогоном.

- **Чистый клон.** Клон во временную папку прошёл путь от `npm ci` до запущенного production-сервера только по шагам README.
- **Независимое ревью.** Его делал отдельный агент Claude Code. Он получил ТЗ и карту файлов, но не историю разработки, и менять репозиторий ему было запрещено. Агент прочитал весь код, прогнал тесты и пробные скрипты на временной БД. Итог: серьёзных и средних проблем нет, 10 мелких находок и замечание к тесту. Вторую модель другого семейства не подключали.
- **Каждую находку ИИ проверил сам, прежде чем её принять:** красным тестом, замером на работающем сервере или чтением кода. Вывод агента считался черновиком, а не фактом.

- **Находки 4 и 7 ИИ предложил оставить ограничениями**, решение за человеком. Итоги отчёта точные, а подгонка под округлённые строки исказила бы их. Живой таймер ошибается, только если на компьютере пользователя неверно выставлено время, а отчёт от этого не зависит. Оба ограничения и способы их снять описаны в README.
- **Ошибка ИИ, которую подсветило ревью.** Агент отметил, что никто не проверял текст ошибки UNIQUE на Turso, а от него зависит распознавание повторного старта. Комментарий в коде, который ИИ написал на этапе 1, утверждал, что текст тот же. Комментарий исправлен, проверка внесена в этап 7.
- **Ложная тревога без «исправлений».** После правок страница отчёта будто зависла на «Загрузка…». Ошибок в консоли и на сервере не было, поэтому ИИ ничего не менял, пока не нашёл причину. Повторная загрузка отрисовала отчёт: текст был прочитан до гидратации, в скрытой панели браузера сразу после перекомпиляции.
- **Тест должен уметь падать.** Если тест писался после кода, его проверяли на старом коде или с убранной частью исправления:
  - e2e-тесты отчёта упали на коде без исправления;
  - тест фокуса с задержанным запросом упал, когда из кода убрали проверку «пользователь уже ушёл в другое поле»;
  - строгий тест индекса упал с неверной колонкой в ожидании.

## Найденные и исправленные ошибки

### № 1. На Windows файл базы не удаляется после закрытия клиента

- **Где:** тесты на Windows.
- **Симптом:** удаление файла БД после `client.close()` падает с `EBUSY`.
- **Причина:** libSQL держит файл открытым, пока сборщик мусора не уничтожит нативные объекты подготовленных выражений, включая пробный `SELECT 1` внутри `createClient`. Это подтверждено экспериментом: после принудительного `gc()` файл удаляется сразу.
- **Как нашли:** smoke-тесты упали на этапе уборки; ошибку воспроизвели отдельным скриптом вне Vitest.
- **Исправление:** вместо удаления после каждого теста — один временный корень на весь прогон. Он удаляется после завершения воркеров (`tests/global-setup.ts`).
- **Страж:** smoke-тесты; после прогона в `%TEMP%` не остаётся папок.
- **Коммит:** `364aaea`.

### № 2. Лишний PRAGMA для внешних ключей

- **Где:** `openDatabase`.
- **Симптом:** лишний код и неверный комментарий.
- **Причина:** ИИ перенёс на libSQL поведение стандартного SQLite («внешние ключи выключены по умолчанию») и добавил `PRAGMA foreign_keys = ON`.
- **Как нашли:** тест «PRAGMA на параллельных соединениях» прошёл сразу, хотя должен был упасть. Это заставило перепроверить допущение. Оказалось, libSQL включает и соблюдает внешние ключи по умолчанию.
- **Исправление:** `PRAGMA` удалён. Теперь тест проверяет поведение, а не флаг: строка со ссылкой на несуществующего родителя отклоняется.
- **Страж:** тест S3 в `tests/smoke/db.test.ts`.
- **Коммит:** `364aaea`.

### № 3. Ошибка сертификата при установке пакетов

- **Где:** окружение.
- **Симптом:** `npm install` падает с `SELF_SIGNED_CERT_IN_CHAIN`.
- **Причина:** прокси-шлюз сети вскрывал HTTPS. ИИ сначала предположил антивирус и посоветовал добавить его сертификат в доверенные. **Совет был ошибочным** и отозван.
- **Как нашли:** проверка цепочки сертификатов (`openssl s_client`) показала чужой корневой центр.
- **Исправление:** проверку TLS не отключали и чужому сертификату доверие не давали; зависимости поставлены из другой сети.
- **Страж:** нет.
- **Коммит:** нет.

### № 4. Флаг регулярного выражения, недоступный при target ES2017

- **Где:** `tests/integration/schema.test.ts`.
- **Симптом:** `tsc` выдаёт `TS1501: This regular expression flag is only available when targeting 'es2018' or later`.
- **Причина:** ИИ написал регулярное выражение с флагом `s` (dotAll), а в `tsconfig` скаффолда стоит `target: ES2017`.
- **Как нашли:** `npm run check`, шаг проверки типов. Сам Vitest типы не проверяет, и тест там проходил.
- **Исправление:** флаг убран, потому что SQL индекса умещается в одну строку. Цель компиляции ради теста не меняли.
- **Страж:** `npm run typecheck` локально и в CI.
- **Коммит:** `a0d1bb7`.

### № 5. Изменяющие запросы принимались с другого сайта и в виде text/plain

- **Где:** `src/server/http/handlers.ts`.
- **Симптом:** межсайтовый POST и POST с `Content-Type: text/plain` создавали сотрудника.
- **Причина:**
  - обработчики не проверяли ни `Sec-Fetch-Site`, ни `Content-Type`;
  - `request.json()` разбирает тело независимо от заявленного типа;
  - «простой» межсайтовый POST с `text/plain` браузер отправляет без предварительного CORS-запроса.
- **Как нашли:** на риск указало автоматическое ревью безопасности. ИИ написал тесты, и они упали: вместо 403 и 415 приходил ответ 201.
- **Исправление:** функция `assertSameSiteJson` в обработчиках добавления сотрудника, старта и стопа таймера:
  - 403, если браузер пометил запрос как `cross-site` или `same-site`;
  - 415, если тело не объявлено как JSON.

  Запросы без `Sec-Fetch-Site`, например из `curl`, проходят.

- **Страж:** `tests/api/request-guard.test.ts`.
- **Коммит:** `cecaf55`.

### № 6. На телефоне строка с идущим таймером выходила за экран

- **Где:** `src/components/employees/employee-row.tsx`.
- **Симптом:** при ширине 375 px страница становилась шире на 107 px (`scrollWidth` 482), кнопка «Остановить» уходила за край.
- **Причина:** у flex-элемента по умолчанию `min-width: auto`, поэтому он не сжимается уже своего содержимого. А однострочное описание задачи (`truncate`, то есть `white-space: nowrap`) задавало минимум, равный всей длине текста.
- **Как нашли:** проверка в браузере на мобильной ширине, замер геометрии DOM.
- **Исправление:**
  - `min-w-0` на блоке строки;
  - на узких экранах описание переносится на отдельную строку, часы и кнопка уходят под него.
- **Страж:** ручная проверка; автоматическую добавит e2e-тест на этапе 5.
- **Коммит:** `a8f4577`.

### № 7. Опоздавший стоп мог остановить новый таймер

- **Где:** API таймера, раньше `POST /api/employees/:id/timer/stop`.
- **Симптом:** стоп, нажатый, пока сервер лежал, сработал после его запуска. Если бы за это время запустили новый таймер, опоздавший запрос остановил бы его.
- **Причина:**
  - стоп означал «остановить то, что сейчас идёт у сотрудника», а не конкретную запись, поэтому повторная доставка запроса меняла результат;
  - сам повтор отправил браузер: в сетевом журнале запрос сначала падает с `ERR_CONNECTION_REFUSED`, а потом повторяется с ответом 200.
- **Как нашли:** при ручной проверке «сервер недоступен». Подтвердили сверкой времени окончания записи и сетевым журналом.
- **Исправление:** `POST /api/time-entries/:id/stop` закрывает только эту запись и только пока она идёт. Повтор даёт 409, неизвестная запись — 404.
- **Страж:** тест «ignores a late repeat of a stop…» в `tests/integration/timer.test.ts` и тесты обработчиков.
- **Коммит:** `28c3efb`.

### № 8. После горячей перезагрузки dev-сервер отвечал старым кодом сервиса

- **Где:** `src/server/http/container.ts`.
- **Симптом:** после добавления `stopEntry` запущенный `npm run dev` отвечал 500: `service.stopEntry is not a function`.
- **Причина:** чтобы горячая перезагрузка не открывала новое подключение к БД, в `globalThis` хранился весь объект сервиса. Модули обновились, а объект остался старым. Тесты этого не видят: каждый создаёт свой сервис.
- **Как нашли:** проверка нового стопа в браузере, стек ошибки в серверном логе.
- **Исправление:** в `globalThis` остался только клиент БД, а сервис кэшируется на уровне модуля и после перезагрузки собирается заново. В продакшене горячей перезагрузки нет, его ошибка не затрагивала.
- **Страж:** ручная проверка; кэш задокументирован комментарием в коде.
- **Коммит:** `b0fb169`.

### № 9. Стоп отвечал 500, если часы сервера отстают от времени старта

- **Где:** `stopEntry` в `src/server/tracking/service.ts`.
- **Симптом:** API отвечал 500 «Внутренняя ошибка», и таймер нельзя было остановить, пока часы сервера не догонят время старта.
- **Причина:** `ended_at = now` нарушал ограничение `CHECK (ended_at >= started_at)`. Так бывает, если часы сервера шагнули назад или старт и стоп обслужили два сервера с немного разными часами, как на бессерверном хостинге.
- **Как нашли:** независимое ревью, пробный скрипт: если часы на секунду отстают от времени старта, стоп даёт 500, а если на 2 секунды впереди — 200. ИИ подтвердил красным тестом.
- **Исправление:** `ended_at = max(now, started_at)` в том же единственном `UPDATE`. Такая запись получает нулевую длину, а не ошибку.
- **Страж:** тест «still stops when the server clock has stepped back behind the start» в `tests/integration/timer.test.ts`.
- **Коммит:** `9b2e84a`.

### № 10. Приложение можно было показать в невидимом фрейме (кликджекинг)

- **Где:** `next.config.ts`.
- **Симптом:** ни одна страница не отправляла `X-Frame-Options` или `frame-ancestors`.
- **Причина:** Next.js не ставит эти заголовки сам. Чужой сайт мог показать доску в невидимом фрейме и обманом заставить нажать «Остановить». Такой клик — запрос того же сайта, поэтому защита от межсайтовых запросов его пропускает, а README обещал, что чужой сайт не сможет записать данные через браузер посетителя.
- **Как нашли:** независимое ревью; ИИ подтвердил по заголовкам ответов работающего сервера.
- **Исправление:** `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` и `X-Content-Type-Options: nosniff` для всех ответов через `headers()` в `next.config.ts`.
- **Страж:** `tests/unit/security-headers.test.ts` проверяет конфиг, e2e-тест — заголовки, которые реально отдаёт production-сборка.
- **Не проверено:** настоящую атаку через фрейм в браузере не воспроизводили.
- **Коммит:** `565d76b`.

### № 11. Успешный ответ не в JSON ронял список сотрудников

- **Где:** `src/lib/api-client.ts`.
- **Симптом:** если между браузером и приложением кто-то отвечает 200 с HTML (страница входа прокси или публичного Wi-Fi), список падал на `null.length`.
- **Причина:** когда тело не разбиралось как JSON, клиент возвращал `null` под видом данных.
- **Как нашли:** независимое ревью, по чтению кода; ИИ подтвердил красным тестом.
- **Исправление:** такой ответ превращается в `ApiError` с кодом `BAD_RESPONSE` и сообщением «Сервер ответил не так, как ожидалось. Обновите страницу.»
- **Страж:** тест «rejects a successful answer that is not JSON…» в `tests/unit/api-client.test.ts`.
- **Коммит:** `f20b43b`.

### № 12. Невидимое имя создавало сотрудника; сообщения об ошибках по-английски

- **Где:** `src/server/tracking/validation.ts`.
- **Симптом:** имя из одного символа нулевой ширины (U+200B) создавало сотрудника, которого не видно в списке; имя «...» тоже проходило. На тело неверного типа API отвечал сообщением zod по-английски.
- **Причина:** `trim()` не убирает невидимые символы, а для ошибок типа не были заданы свои сообщения.
- **Как нашли:** независимое ревью, пробный запрос; ИИ подтвердил красными тестами.
- **Исправление:** в имени и описании задачи должна быть хотя бы одна буква или цифра (`/[\p{L}\p{N}]/u`); для неверного типа поля и тела — русские сообщения.
- **Страж:** таблицы тестов «rejects %s with a message in Russian» в `tests/integration/employees.test.ts` (невидимый символ, одна пунктуация, неверный тип поля и тела) и «are rejected: %s» для описания задачи в `tests/integration/timer.test.ts`.
- **Коммит:** `6ab1191`.

### № 13. Ответы на перезагрузку списка могли прийти не по порядку

- **Где:** `src/components/employees/employees-board.tsx`.
- **Симптом (по коду):** перезагрузка при возврате на вкладку и перезагрузка после «Начать» или «Остановить» могут пересечься. Если старый ответ придёт последним, на экране останется прошлое состояние — например, остановленный таймер будет показан идущим.
- **Причина:** у перезагрузки списка не было упорядочивания, в отличие от отчёта.
- **Как нашли:** независимое ревью, по чтению кода. Вживую не воспроизводили: нужен точный порядок двух ответов.
- **Исправление:** помощник `createLatestGate` выдаёт каждой перезагрузке номер, и обновить экран может только самая новая.
- **Страж:** `tests/unit/latest-gate.test.ts`.
- **Коммит:** `f679859`.

### № 14. В отчёте не было видно даты окончания записи

- **Где:** `src/components/report/report-table.tsx`, `src/lib/format.ts`, `src/server/tracking/report.ts`.
- **Симптом:** ночная смена выглядела как «26 октября 22:00–01:30», то есть как несколько часов в первый день. Запись, обрезанная границей периода, показывала полное время начала и конца рядом с меньшей длительностью.
- **Причина:** строка записи показывала только дату начала и не сообщала, что посчитана лишь часть записи.
- **Как нашли:** независимое ревью, по чтению кода; ИИ подтвердил красными тестами и проверил в браузере на вымышленной ночной записи.
- **Исправление:**
  - `formatEntryTimes` добавляет дату окончания, если запись кончилась в другой день: «22:00 – 27 октября 01:30»;
  - `buildReport`, который и обрезает записи по периоду, помечает такие записи флагом `isClipped`, и строка читается как «1 ч 30 мин в периоде».
- **Страж:** тесты `formatEntryTimes` в `tests/unit/format.test.ts` (в заданном часовом поясе) и тесты `isClipped` в `tests/unit/report.test.ts`.
- **Коммит:** `f0c67a6`.

### № 15. Отчёт устаревал и не говорил об этом

- **Где:** `src/components/report/report-board.tsx`, `report-table.tsx`.
- **Симптом:** идущие таймеры считаются до момента ответа сервера. Отчёт, оставленный открытым во вкладке, показывал старые цифры и никак этого не обозначал.
- **Причина:** время подсчёта не показывалось, а отчёт сам не обновлялся.
- **Как нашли:** независимое ревью, по чтению кода; ИИ подтвердил красными e2e-тестами.
- **Исправление:** строка «Посчитано на 11:56» и пересчёт при возврате на вкладку. Показанный отчёт остаётся на месте, пока не придёт новый, поэтому экран не мигает «Считаю…».
- **Страж:** e2e-тесты «the report says when it was counted» и «the report recounts on return to the tab without clearing the screen»; второй задерживает запрос и проверяет, что старый отчёт виден.
- **Коммит:** `265b67d`.

### № 16. После «Начать» и «Остановить» терялся фокус клавиатуры

- **Где:** `src/components/employees/employee-row.tsx`.
- **Симптом:** после старта или стопа фокус уходил на саму страницу, и пользователю клавиатуры или скринридера приходилось заново проходить всю страницу.
- **Причина:** старт заменяет поле задачи кнопкой «Остановить», стоп возвращает поле обратно. Элемент с фокусом исчезал, а нажатая кнопка ещё и отключалась на время запроса.
- **Как нашли:** независимое ревью, по чтению кода; ИИ подтвердил красным e2e-тестом.
- **Исправление:** когда строка обновилась, фокус переходит к следующему шагу: после старта на «Остановить», после стопа — в поле задачи. Это делает только строка, где действовал пользователь, и только если он не перевёл фокус в другое место, пока шёл запрос.
- **Страж:** e2e-тесты «the keyboard focus stays in the row after starting and stopping» (только клавиатура) и «a slow start does not pull the focus back once the user has moved on».
- **Коммит:** `3e1540c`.

### № 17. Тест в обход сервиса принимал любую ошибку

- **Где:** `tests/integration/timer-restart.test.ts`.
- **Симптом:** тест «is enforced by the database itself…» проверял только то, что вставка падает, — с любой ошибкой.
- **Причина:** ИИ написал `rejects.toThrow()` без условия. Тест прошёл бы и при ошибке внешнего ключа или опечатке в названии колонки.
- **Как нашли:** независимое ревью.
- **Исправление:** тест ждёт именно `UNIQUE constraint failed: time_entries.employee_id` в ошибке драйвера, которую оборачивает Drizzle, — тот же текст, по которому сервис распознаёт повторный старт. С другой колонкой в ожидании тест падает.
- **Страж:** сам тест.
- **Коммит:** `b7c1252`.
